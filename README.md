# Support Prompt Lab

Небольшой проект по промпт-инжинирингу: классификация обращений в поддержку и проверка качества ответов по заранее размеченным примерам.

Проект показывает полный цикл работы с промптом: постановку задачи, базовую версию инструкции, уточнение правил, обработку неоднозначных запросов и автоматическую проверку результата. Код написан на Python и использует только стандартную библиотеку.

**Деморежим работает без API-ключа и без интернета.** Для получения новых ответов модели предусмотрен отдельный запуск через OpenAI API.

## Задача

Сотруднику поддержки нужно быстро понять, к какой теме относится обращение, насколько оно срочное и достаточно ли информации для первичной классификации.

На вход подаётся текст обращения. На выходе — JSON:

```json
{
  "category": "billing",
  "priority": "high",
  "needs_clarification": false,
  "reason": "За одну подписку произошло повторное списание."
}
```

Классификатор помогает сортировать обращения. Он не отправляет ответы клиентам и не выполняет действия с аккаунтами или платежами.

## Формат результата

| Поле | Возможные значения | Назначение |
|---|---|---|
| `category` | `billing`, `technical`, `account`, `other` | Тема обращения |
| `priority` | `low`, `normal`, `high` | Приоритет по правилам проекта |
| `needs_clarification` | `true`, `false` | Нужно ли уточнить суть обращения |
| `reason` | Непустая строка | Короткое объяснение на русском |

Категории:

- `billing` — оплата, возвраты, тарифы, счета и списания;
- `account` — вход, пароль, профиль, удаление или захват аккаунта;
- `technical` — ошибки функций сервиса, кроме входа и оплаты;
- `other` — остальные темы, пустые и непонятные обращения.

## Две версии промпта

### v1 — базовая инструкция

[prompts/v1.txt](prompts/v1.txt) описывает задачу, допустимые значения и формат ответа. Она оставляет модели свободу в интерпретации срочности и неоднозначных сообщений.

### v2 — инструкция с явными правилами

[prompts/v2.txt](prompts/v2.txt) добавляет:

- определения категорий и приоритетов;
- порядок выбора темы, если в обращении несколько проблем;
- правила для пустого текста, отрицаний и нехватки информации;
- разделение текста обращения и инструкций классификатора;
- два примера желаемого ответа (few-shot prompting).

Например, слово «СРОЧНО» само по себе не повышает приоритет. Повторное ошибочное списание, признаки захвата аккаунта и недоступность сервиса для всей команды получают `high`. Обычные информационные вопросы и предложения функций получают `low`.

Эти правила — условия учебной задачи. Для реального сервиса их нужно согласовать с командой поддержки.

Обе версии используют одинаковую JSON Schema на уровне API. Поэтому корректный формат нельзя приписывать только улучшению текста промпта: формат дополнительно ограничивается механизмом Structured Outputs.

## Быстрый запуск

Требуется **Python 3.10 или новее**. Установка пакетов не нужна.

```bash
git clone https://github.com/egorryabushko/support-prompt-lab.git
cd support-prompt-lab
python3 prompt_lab.py demo
```

На Windows вместо `python3` можно использовать `py`.

Команда загружает 12 обращений и два файла с учебными ответами, проверяет их и выводит сводку. Подробный результат сохраняется в `reports/demo/report.md` и `reports/demo/report.json`.

**Ответы в `examples/` составлены вручную для демонстрации работы проверок. Они не получены от модели.** Числа деморежима не являются измерением качества LLM и не доказывают преимущество v2. При изменении промпта демоответы автоматически не меняются: для проверки новой версии нужен запуск API.

В учебных ответах v1 полностью проходят 5 из 12 кейсов, v2 — 11 из 12. В v2 намеренно сохранена ошибка: сообщение «Не работает. Помогите» отнесено к `technical`, хотя по правилам проекта ожидается `other` с запросом уточнения. Это позволяет увидеть разбор ошибки в отчёте.

## Запуск с моделью

Для этого режима нужен собственный ключ OpenAI API и доступ к выбранной модели. Запросы оплачиваются по тарифам провайдера. Деморежим запросов не делает.

Установите ключ в переменную окружения. Пример для macOS/Linux, ввод без отображения ключа в терминале:

```bash
read -s -p "OPENAI_API_KEY: " OPENAI_API_KEY
export OPENAI_API_KEY
```

PowerShell:

```powershell
$env:OPENAI_API_KEY = Read-Host "OPENAI_API_KEY" -MaskInput
```

`-MaskInput` требует PowerShell 7.1+. Файл `.env.example` показывает имя настройки; `.env` автоматически не загружается. Ключ не следует добавлять в репозиторий.

Классификация одного обращения:

```bash
python3 prompt_lab.py classify --version v2 --model gpt-4o-mini --text "За подписку списали деньги дважды"
```

Модель передаётся явно через `--model`. При необходимости укажите другую доступную вам модель с поддержкой Responses API и Structured Outputs.

Сравнение двух промптов на одном наборе обращений:

```bash
python3 prompt_lab.py evaluate --model gpt-4o-mini
```

Это **24 последовательных запроса**: 12 обращений × 2 версии. Для отдельного каталога результатов:

```bash
python3 prompt_lab.py evaluate --model gpt-4o-mini --out reports/experiment-01
```

Скрипт сохраняет ответы после каждого запроса. Ошибки API записываются в итоговый отчёт и учитываются как неуспешные ответы; при их наличии команда завершается с ненулевым кодом. Автоматических повторов запросов нет. Если запуск прерван, сохранённые ответы остаются на диске, но продолжение с места остановки не реализовано. Повторный запуск в том же каталоге перезаписывает результаты.

Используется OpenAI Responses API: системная инструкция передаётся отдельно от текста обращения, результат ограничивается JSON Schema, для запроса задаётся `store: false`. Описание формата API: [официальная документация OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

Режим API передаёт текст обращения провайдеру модели. В репозитории используются только вымышленные обращения. Результаты API сохраняются локально в `reports/`, который исключён из Git.

## Проверочный набор

[data/cases.json](data/cases.json) содержит 12 синтетических обращений с ожидаемыми значениями трёх полей:

- обычные вопросы об оплате, входе и работе сервиса;
- предложение новой функции;
- повторное списание и признаки захвата аккаунта;
- массовую недоступность;
- эмоциональную формулировку без оснований для высокого приоритета;
- пустой и неоднозначный ввод;
- отрицание проблемы;
- попытку подменить инструкции внутри обращения (prompt injection).

Проверочные обращения не повторяют два примера из v2, но сам набор открыт и используется при разработке. Это небольшой набор для отладки и регрессионных проверок, а не независимый закрытый тест.

## Как считается результат

Для каждой версии считаются:

1. **Валидность формата** — все четыре поля присутствуют, лишних полей нет, значения и типы допустимы.
2. **Точность категории, приоритета и уточнения** — доля точных совпадений с разметкой отдельно по каждому полю.
3. **Полностью верные кейсы** — корректный формат и совпадение всех трёх оцениваемых полей одновременно.

Пропущенные ответы и невалидные объекты остаются в общем числе кейсов и считаются ошибками по всем полям. Неизвестные ID отклоняются. Для `reason` автоматически проверяется только непустая строка; соответствие объяснения тексту нужно оценивать вручную.

JSON-отчёт содержит исходный текст, ожидаемый ответ, фактический ответ, результаты проверок, имя модели, время запуска в UTC и SHA-256 промптов и набора кейсов. Это помогает сопоставлять результаты с конкретными версиями файлов.

## Проверка кода

```bash
python3 -m unittest discover -s tests -v
```

Тесты проверяют расчёт метрик, пропуски, тип boolean, неверные значения, лишние поля, повторяющиеся ID, запись отчёта, обработку ответа и отказа модели. API заменяется тестовой заглушкой; ключ и сеть для тестов не нужны.

## Ограничения и развитие

Проект демонстрирует процесс работы с промптами, но не заявляет готовность к промышленному использованию. Живые результаты API в репозитории пока не опубликованы. Малый синтетический набор не позволяет оценить качество на реальном потоке обращений; отдельный кейс инъекции не доказывает устойчивость ко всем атакам. Повторные вызовы модели могут давать разные ответы.

Следующие шаги: собрать обезличенные реальные обращения, согласовать разметку с поддержкой, выделить закрытый тестовый набор, повторить сравнение на нескольких запусках и вручную проверить объяснения. При оценке нового промпта нужно сохранять одну модель и одинаковые настройки для обеих версий.

Код и документация подготовлены с помощью ИИ; проект открыт для дальнейших изменений.
